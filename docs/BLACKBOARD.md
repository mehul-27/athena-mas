# The Athena Blackboard

Agents run in **separate processes** (the CrewAI analyst is its own A2A server;
ADK agents run elsewhere). They therefore cannot share Python objects. They
exchange a `run_id` over A2A and **read and write the blackboard themselves**.

The blackboard is a shared persistent store:

- **`BlackboardStore`** (`store.py`) is the interface. `SQLiteStore`
  (`sqlite_store.py`) is the local backend; a cloud backend implements the same
  interface.
- **Every write is attributable.** Each row records the author and a version,
  and each mutation is copied into an append-only `history` table. Nothing in
  the application can update or delete history — SQLite triggers abort it.
- **Values are validated** against their section's Pydantic model on write *and*
  on read, so a corrupted row fails loudly instead of leaking a bad shape.

## Sections

| Section | Model | Written later by | Kind |
|---|---|---|---|
| `task` | `Task` | the entry point (API / CLI), at run creation | single |
| `plan` | `Plan` | planner | single |
| `evidence` | `list[EvidenceItem]` | researcher(s), tool users | list (append) |
| `draft` | `Draft` | writer | single |
| `critique` | `Critique` | critic | single |
| `guardrail_flags` | `list[GuardrailFlag]` | guardrails | list (append) |
| `final_report` | `FinalReport` | writer, at the end | single |

`FinalReport` is the course-mandated structured output. `to_markdown()` renders
it with a citations table.

## Concurrency rules

The store is safe for multiple threads **and** multiple processes sharing one
database file (WAL, `busy_timeout`, `BEGIN IMMEDIATE`, one short transaction per
operation).

- **`write` replaces a whole section.** It returns the new version. Pass
  `expected_version` to opt into optimistic concurrency: if another agent wrote
  first, you get `VersionConflictError` and should re-read and retry. A section
  that has never been written is at version 0, so `expected_version=0` means
  "create it only if nobody has".
- **`append` adds one item to a list section.** Use it for `evidence` and
  `guardrail_flags`: several agents can append at the same time without
  clobbering each other, because each append is serialised inside its own
  transaction. It also returns the new section version.
- **Never `write` a list section while others append to it** — that replaces
  their items. That is what `expected_version` is for if you must.

Version numbers are per section, not per run.

## Example: two parallel researchers

```python
# researcher_a.py
bb = Blackboard.open(run_id)
bb.append("evidence", EvidenceItem(id="a1", source_type="rag",
          source_ref="doc-17", content=..., retrieved_by="researcher_a"),
          author="researcher_a")

# researcher_b.py, running at the same time
bb = Blackboard.open(run_id)
bb.append("evidence", EvidenceItem(id="b1", source_type="web",
          source_ref="https://example.com", content=..., retrieved_by="researcher_b"),
          author="researcher_b")
```

Neither write is lost: the final `evidence` section holds both items, and
`history()` shows which agent contributed which, in order.

## Inspecting a run

```python
bb = Blackboard.open(run_id)
bb.snapshot()   # {"run_id": ..., "sections": {name: model}, "versions": {name: int}}
bb.history()    # [{seq, section, operation, author, version, timestamp, value}, ...]
```

## Known limits (what changes for cloud)

- SQLite is single-file and single-host. A hosted backend needs the same six
  methods, plus a server-side compare-and-set for `expected_version` and an
  atomic append.
- Timestamps are generated by the store process; with multiple hosts, clock skew
  becomes visible. `seq` remains the authoritative order.
- There is no expiry or GC: history grows forever by design.
