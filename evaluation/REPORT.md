## Interpretation
- **Sample size.** hierarchical n=70, p2p n=1, parallel n=2, sequential n=2. Every group is far below the 8 runs per pattern that would make a difference in central tendency stable, and the four patterns were run on the same prompts, so the same prompt-level difficulty appears in every column.
- **Treat every comparison as indicative.** The smallest group has n=1. A single run moving between success and failure changes its pattern's success rate by 100 percentage points.
- **Latency spread.** hierarchical median 60.085s (IQR 59.995-119.607, range 32.907-699.409), p2p median 537.311s (IQR 537.311-537.311, range 537.311-537.311), parallel median 19610.032s (IQR 10047.897-29172.166, range 485.763-38734.301), sequential median 335.992s (IQR 294.111-377.873, range 252.23-419.754).
- **Too few runs per pattern to compare spread.** With fewer than four runs in a group the quartiles collapse onto single observed values, so overlap between groups says nothing; only the raw ranges above should be read.
- **Answer quality spread.** hierarchical median 0 (n=70), p2p median 0.15 (n=1), parallel median 0.075 (n=2), sequential median 0.075 (n=2).
- **Quality differences here are a handful of runs wide.** With fewer than four scored runs in a group, a single criterion flipping on one run moves that pattern's median by tens of percentage points of rubric weight.
- **Tokens per run.** hierarchical 0 tokens (n=70), p2p 31471 tokens (n=1), parallel 17690 tokens (n=1), sequential 16759 tokens (n=1).
- **No pattern is called best.** `hierarchical` has the lowest median latency in this batch, while `p2p` spends the most tokens per run; latency, tokens spent and answer quality move independently here, and the harness records them separately for exactly that reason. A pattern that is quick because it researches less is not a better orchestrator, and one that is slow because it spends more tokens is not a worse one.
- **Cost is unpriced, not zero.** 75 of 75 runs record `est_cost_usd = null` because the configured model (groq/qwen/qwen3.8-27b) has no rate in `evaluation/config.json` or `data/pricing.json`. No total, median or per-pattern cost comparison is made: the cost columns are absent rather than filled with an invented rate. Token counts are the only comparable proxy for spend in this batch, and the provider's actual bill is not observable from here.
- **Non-completions are included, not dropped.** completed=5, error=1, failed=68, timeout=1. A run that failed, timed out or errored keeps its latency and its failure labels in the tables above, so a pattern cannot look fast or accurate by losing its unfinished runs.
- **Timeouts censor the latency medians.** A timed-out run stops at the per-run timeout, so its recorded latency is the cap rather than the time it would have taken; the true latency of those runs is at least what is recorded.
- **Success is defined by the rubric, not by the system's own critic.** `scoring.CRITIC_IS_GROUND_TRUTH` is False; the critic's verdict is reported separately so the two can disagree in public.
- **The rubric is deterministic and keyword-based.** It checks answer-key coverage, citations that resolve to captured evidence, required output structure and the security rules. It cannot tell whether a sentence is semantically supported, so a fluent wrong answer and a terse right answer can both land near the same score.
- Descriptive comparison only: n is small and no significance test is applied. Differences are not claims about the population.
